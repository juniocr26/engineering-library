## Purpose and running composition

The project demonstrates how a committed business fact reaches a broker and produces one local inventory effect despite duplicate transport. Rust/Axum/Tokio compose three Supervisor-managed processes: HTTP, relay worker and inventory consumer. PostgreSQL stores producer facts, outbox/retry/ownership and consumer effects. RabbitMQ carries canonical envelopes. Vue supplies both real local operations and explicitly illustrative educational playback. This application has no verified runtime integration with another portfolio repository.

One main Compose environment runs app, frontend, PostgreSQL and RabbitMQ. The supported launcher validates local example-derived configuration, builds locked runtime artifacts, checks migration history and performs protected backup/disposable restore before necessary forward migrations. Direct Compose startup is not equivalent to that retained-storage procedure. Historical `compose.demo.yaml` is not a second permanent demo stack. Defaults are frontend localhost:5173, HTTP localhost:8080, PostgreSQL localhost:5433 and RabbitMQ management localhost:15672. Internal readiness/metrics addresses belong separately to HTTP/relay/consumer on 9100/9101/9102; `/health` alone proves only HTTP liveness.

## Producer and outbox are one local commit

A fixed producer intent contains stable request identity and a supported scenario. The PostgreSQL producer transaction inserts a run, stock fixture 10, goods-receipt business fact and outbox envelope with quantity 5. Repeating the same request identity and intent returns existing evidence; conflicting intent is rejected. `demo.goods_receipts` proves the producer fact. It does not prove that the consumer has added five units. A failed response after COMMIT can hide success, so recovery inspects the same request rather than manufacturing another identity.

`relay.outbox_events` stores the canonical event, immutable identity/content and mutable publication state. Acquisition uses database time, short locks and `FOR UPDATE SKIP LOCKED`. Pending state, availability, lease expiry and budget constrain eligibility. A committed acquisition increments lifetime `attempt_count` and state revision, even if the worker crashes before sending. Retry cycles record a baseline and maximum, preserving lifetime history. Ownership token/revision/lease protect later transitions, but cannot prevent an expired process from sending to an external broker.

## Broker acceptance and durable completion are separate

The publisher sends the original stable-ID envelope with mandatory routing and observes confirms/returns. Known unroutable/rejected results differ from uncertainty. Missing confirm can conceal acceptance; losing a SQL completion acknowledgement can conceal processed state. A later acquisition may republish after acceptance and before completion. Replacing a broken connection only repairs the publisher lifecycle; it does not decide what happened previously.

Durable retry persists the next eligible time and sanitized failure state, using capped exponential equal jitter (initial ceiling 1 second, cap 5 minutes). A worker sleep is merely admission pacing. Terminal `dead_letter` preserves exhausted/unrecoverable work in SQL. Bounded discovery identifies maintenance candidates; a snapshot cannot authorize mutation, so the adapter rereads and requires current authority. Authorized replay uses an operator identity, request identity, expected state/revision and durable audit. A new cycle preserves event identity and lifetime count; replay can yield a consumer duplicate. Demo credentials and replay authority are different contracts.

## Exactly one local stock effect under the deduplication contract

The consumer validates envelope/message identity and supported inventory intent. In READ COMMITTED, it first attempts a unique `(consumer_name,event_id)` receipt insertion, then updates stock and completes that receipt atomically. A conflicting insertion waits for the winner; a fresh statement snapshot reads its committed receipt. Duplicate classification compares restored immutable model content, not just the ID. Versioned BYTEA avoids losing representation through JSONB number/timestamp normalization. A changed envelope with the same identity must not silently become a valid duplicate.

Deferred constraints require complete receipts at commit; guards protect completed identity/content against ordinary mutation/removal. They do not protect against privileged database owners. Normal delivery changes 10 → 15 with one receipt. Equal duplicate and concurrent duplicate keep stock 15 and one effect. This guarantee concerns the supported local SQL effect with retained receipt identity; email, payment or another external side effect cannot join that transaction automatically.

Only after durable processing does the consumer attempt manual ACK. Broker acceptance, outbox completion, consumer commit, local ACK send and broker receipt of ACK are five distinct observations. The consumer may commit before relay completion is observed. ACK send success does not prove broker receipt; redelivery remains possible. There is no exactly-once transport claim.

Invalid/unsupported/conflicting input uses application-managed quarantine: preserve the supported original content with a confirmed quarantine publication before source ACK. If preservation fails or cannot represent the input within bounds, keep the source without ACK. SQL terminal outbox state is different from a RabbitMQ quarantine queue. Default topology is direct durable `relay.events`, key `event`, queue `relay.local` in vhost `relay`; quarantine uses `relay.quarantine`, key `inventory`, queue `relay.quarantine.inventory`.

## Real UI, bounded actions and honest evidence

Real scenarios are normal delivery, duplicate, concurrent duplicate and one run-scoped before-send rejection followed by durable retry. Duplicate actions republish the original envelope through action-specific `relay.demo.<action UUID>` queue/routing key and bounded temporary consumers. Their publications and Duplicate classifications correlate by action/run/event; aggregate broker graphs cannot establish that relationship. Observation counts are capped and therefore lower bounds.

The controlled rejection is not a broker outage or NACK. Crash, race and lost-confirmation/ACK animations illustrate distributed failure windows without manipulating infrastructure. Actual crash/reconnect, lease race, commit ambiguity and consumer-failure schedules belong to isolated integration tests. Simulations make temporal uncertainty understandable without claiming that the UI caused those faults.

The Vue client uses HTTP through a proxy, not WebSocket AMQP delivery. POST `/demo/runs` and `/demo/actions` create fixed work; GET run evidence/history/configuration never republishes. `/demo/runs` GET remains the successful-run selector. Separate Bearer credential, origin/client-header checks and finite body/rate/concurrency/deadlines bound the local demo. Token is memory-only in the browser; session storage retains identifiers. These controls are not TLS or application encryption.

History supports retained pending/unknown/terminal work and actions. `observed_at` timestamps a statement snapshot; it becomes stale after 15 seconds. Failed refresh preserves the prior observation, and GET inspection does not resend unknown work. Polling is sequential, at most 60 seconds, with nine-second browser request timeouts. Closing/reloading ends observation, not backend commits. SQL snapshots cannot prove that an absent effect will never commit.

## Records, bounds and operations

`demo` owns runs, goods receipts, actions, publications, consumer observations and controlled faults. `relay` owns outbox and replay audit. `consumer` owns stock and effect receipts. `public._sqlx_migrations` owns applied schema history. Follow one event using read-only filtered queries: producer receipt → outbox status/count/revision → consumer receipt and stock → action/publication/Duplicate observations. Inspect the action queue in RabbitMQ separately. A processed timestamp is not consumer evidence; a broker graph is not an effect receipt.

Bounds include 100 retained runs, 100 total actions, three actions per run, four active runs/actions, one action worker, two temporary contexts, 1–3 publication calls/action and 32 publication/32 consumer observations per run. Capacity rejection preserves history. There is no automatic retention or generic unknown-action repair. Never remove receipts while redelivery remains possible. PostgreSQL backup does not back up RabbitMQ queues. Protected restore, multi-host HA/TLS, broker disaster recovery and larger-scale capacity are separate production work.

## Acceptance, alternatives and learning path

The available final manifest records 243 unique Rust passed entries (241 substantive, two helpers), 27 real-application browser checks, a separate clean installation with 24 browser checks and nine migrations. These results belong to the recorded base/date, not this documentation run; count details and bounded measurements remain in their original evidence. No new chart or capacity extrapolation is justified here. The owner confirmed on 2026-10-18 that the former PDF no longer exists and may be disregarded; its recorded hash remains provenance only.

A single SQL transaction for source/effect is simpler if both belong to one database/process; the outbox plus broker demonstrates durable independent delivery at the cost of duplicate/uncertain windows. Database leases reduce coordination time but cannot fence external effects. Transactional receipts trade durable storage/retention obligations for repeated local-effect safety. Versioned immutable content detects identity reuse at a greater schema/validation cost. These are mechanism consequences and alternatives, not invented original motivations.

Study producer transaction first; then acquisition/token/revision, publisher confirms, durable retry/discovery/replay, consumer transaction/quarantine and finally correlated browser evidence.
