## Evidence and uncertainty

Before a consequential claim, identify project + repository-relative path + symbol/heading + source revision or working-tree status + content hash. Reinspect the relevant current implementation when authorized. Prefer current execution-path evidence over historical prose; a newer document is not automatically authoritative. Keep historical statements dated and identify supersession. State implemented, planned, historical, assumed, reported-unverified and actually verified results separately (`standard-traceability`).

Never invent inspections, test executions, metrics, approvals, capabilities, incidents or personal achievements. A test file or script definition does not establish a pass. Missing evidence requires a precise limitation and targeted next inspection, not a plausible default. Bound negative claims to the inspected scope. Exclude real dotenv values, credentials, private keys, runtime/database data and personal/clinical records before assembling context; do not reproduce them in outputs or logs. Use synthetic examples without private endpoints or payloads. Classification metadata is provenance for release review, not a prohibition against the two authorized collections in this phase.

Preserve official project names, stable project/document IDs, technical symbols, filenames and executable examples. Keep unique semantic `reading-section` keys in both languages and localized heading fragments in links. Do not move documents or silently renumber historical questions.

English and Brazilian Portuguese must preserve the same facts, caveats, failures, units, optional/required wording and normative force (`standard-bilingual`). Translate technical meaning naturally, not just headings. Missing translation is a gap, not an automatic fallback. Compare section keys, identifiers, table rows and examples; structural equality alone does not prove semantic parity.

## Research-informed caller safeguards (draft)

These safeguards guide the explicitly authorized caller. Preserve the canonical standard classifications: an implemented subset does not approve every proposed rule. Historical support, failures and recovery are retained in the private historical-run archive; current campaign status is recorded in the repository-root evaluation report. Publication remains unauthorized.

- Separate source extraction, independent fact review and drafting. Typed JSON and valid syntax do not establish factual correctness. Validate symbol scope, conditional fields, required/default/null distinctions, numeric literals, units, removals and relevant execution headers/modes against the actual code. Prefer deterministic extraction for supported declaration forms; block or request scoped review for unsupported forms.
- Build project/path/revision/hash references from inspected metadata. A model-supplied quotation must match its source bytes; paraphrased or invented quotations are not evidence. Narrow passages to the relevant component and include a verified diff when documenting a change.
- Treat existing documentation as historical claims to compare with current evidence. Remove or revise obsolete claims while preserving still-supported facts. A negative existence claim requires an appropriate complete symbol scope; an omitted excerpt is not proof that a function is absent.
- Let the caller enforce no-op writes: a previously reviewed document and unchanged relevant contract can skip generation and writing. A changed source blob alone does not prove a changed documentation contract; semantic equality must be verified, not guessed. Keep freshness/provenance records separate where needed to avoid rewriting valid prose.
- Preserve raw failures, reviewed authoring examples, held-out cases and future training candidates separately. Identify reviewer corrections and deterministic formatting explicitly; do not attribute supplied facts, validation or bilingual templates to autonomous model success. Keep source/change scenarios disjoint between candidates and held-out evaluation.
- Validate media syntax separately from source support. Corrected diagrams remain reviewer contributions; generated images or diagrams do not establish runtime behavior. Preserve draft/owner-review status and all existing authority and confidentiality boundaries.
