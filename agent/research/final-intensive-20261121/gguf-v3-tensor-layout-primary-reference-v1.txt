L128: GGUF files are structured as follows. They use a global alignment specified in the `general.alignment` metadata field, referred to as `ALIGNMENT` below. Where required, the file is padded with `0x00` bytes to the next multiple of `general.alignment`.
L129: Fields, including arrays, are written sequentially without alignment unless otherwise specified.
L130: 
L131: Models are little-endian by default. They can also come in big-endian for use with big-endian computers; in this case, all values (including metadata values and tensors) will also be big-endian. At the time of writing, there is no way to determine if a model is big-endian; this may be rectified in future versions. If no additional information is provided, assume the model is little-endian.
L132: The `ggml_type` values below mirror `enum ggml_type` in [`include/ggml.h`](../include/ggml.h), which is authoritative and gains new values over time, so readers should take type codes and block sizes from there.

L255: struct gguf_header_t {

L257:     // Must be `GGUF` at the byte level: `0x47` `0x47` `0x55` `0x46`.
L258:     // Your executor might do little-endian byte order, so it might be
L259:     // check for 0x46554747 and letting the endianness cancel out.

L285:     // The number of dimensions in the tensor.
L286:     // Currently at most 4, but this may change in the future.
L287:     uint32_t n_dimensions;

L289:     uint64_t dimensions[n_dimensions];

L292:     // The offset of the tensor's data in this file in bytes.
L293:     //

L295:     // of the file, to make it easier for writers to write the file.
L296:     // Readers should consider exposing this offset relative to the
L297:     // file to make it easier to read the data.
L298:     //

L307:     gguf_tensor_info_t tensor_infos[header.tensor_count];
L308:     // Padding to the nearest multiple of `ALIGNMENT`.
L309:     //
L310:     // That is, if `sizeof(header) + sizeof(tensor_infos)` is not a multiple of `ALIGNMENT`,
L311:     // this padding is added to make it so.
L312:     //
L313:     // This can be calculated as `align_offset(position) - position`, where `position` is
L314:     // the position of the end of `tensor_infos` (i.e. `sizeof(header) + sizeof(tensor_infos)`).
L315:     uint8_t _padding[];

L317:     //
L318:     // This is arbitrary binary data corresponding to the weights of the model. This data should be close
L319:     // or identical to the data in the original model file, but may be different due to quantization or
L320:     // other optimizations for inference. Any such deviations should be recorded in the metadata or as
L321:     // part of the architecture definition.
L322:     //
L323:     // Each tensor's data must be stored within this array, and located through its `tensor_infos` entry.
L324:     // The offset of each tensor's data must be a multiple of `ALIGNMENT`, and the space between tensors
L325:     // should be padded to `ALIGNMENT` bytes.

L329: ## Standardized key-value pairs
L330: 
L331: The following key-value pairs are standardized. This list may grow in the future as more use cases are discovered. Where possible, names are shared with the original model definitions to make it easier to map between the two.
L332: 
L333: Not all of these are required, but they are all recommended. Keys that are required are bolded. For omitted pairs, the reader should assume that the value is unknown and either default or error as appropriate.
L334: The community can develop their own key-value pairs to carry additional data. However, these should be namespaced with the relevant community name to avoid collisions. For example, the `rustformers` community might use `rustformers.` as a prefix for all of their keys.
L335: 
L336: If a particular community key is widely used, it may be promoted to a standardized key.
L337: By convention, most counts/lengths/etc are `uint64` unless otherwise specified. This is to allow for larger models to be supported in the future. Some models may use `uint32` for their values; it is recommended that readers support both.
L338: ### General
L339: #### Required
L340: - **`general.architecture: string`**: describes what architecture this model implements. All lowercase ASCII, with only `[a-z0-9]+` characters allowed. Known values include:
L341:   - `llama`
L342:   - `mpt`
L343:   - `gptneox`
L344:   - `gptj`
L345:   - `gpt2`
L346:   - `bloom`
L347:   - `falcon`
L348:   - `mamba`
L349:   - `rwkv`
L350: - **`general.quantization_version: uint32`**: The version of the quantization format. Not required if the model is not quantized (i.e. no tensors are quantized). If any tensors are quantized, this _must_ be present. This is separate to the quantization scheme of the tensors itself; the quantization version may change without changing the scheme's name (e.g. the quantization scheme is Q5_K, and the quantization version is 4).
L351: - **`general.alignment: uint32`**: the global alignment to use, as described above. This can vary to allow for different alignment schemes, but it must be a multiple of 8. Some writers may not write the alignment. If the alignment is **not** specified, assume it is `32`.

L408: ### LLM
L409: 
L410: In the following, `[llm]` is used to fill in for the name of a specific LLM architecture. For example, `llama` for LLaMA, `mpt` for MPT, etc. If mentioned in an architecture's section, it is required for that architecture, but not all keys are required for all architectures. Consult the relevant section for more information.
L411: - `[llm].context_length: uint64`: Also known as `n_ctx`. length of the context (in tokens) that the model was trained on. For most architectures, this is the hard limit on the length of the input. Architectures, like RWKV, that are not reliant on transformer-style attention may be able to handle larger inputs, but this is not guaranteed.
L412: - `[llm].embedding_length: uint64`: Also known as `n_embd`. Embedding layer size.
L413: - `[llm].block_count: uint64`: The number of blocks of attention+feed-forward layers (i.e. the bulk of the LLM). Does not include the input or embedding layers.
L414: - `[llm].feed_forward_length: uint64`: Also known as `n_ff`. The length of the feed-forward layer.
L415: - `[llm].use_parallel_residual: bool`: Whether or not the parallel residual logic should be used.
L416: - `[llm].tensor_data_layout: string`: When a model is converted to GGUF, tensors may be rearranged to improve performance. This key describes the layout of the tensor data. This is not required; if not present, it is assumed to be `reference`.
L417:   - `reference`: tensors are laid out in the same order as the original model
L418:   - further options can be found for each architecture in their respective sections
L419: - `[llm].expert_count: uint32`: Number of experts in MoE models (optional for non-MoE arches).
L420: - `[llm].expert_used_count: uint32`: Number of experts used during each token token evaluation (optional for non-MoE arches).
L421: #### Attention
L422: - `[llm].attention.head_count: uint64`: Also known as `n_head`. Number of attention heads.
L423: - `[llm].attention.head_count_kv: uint64`: The number of heads per group used in Grouped-Query-Attention. If not present or if present and equal to `[llm].attention.head_count`, the model does not use GQA.
L424: - `[llm].attention.max_alibi_bias: float32`: The maximum bias to use for ALiBI.
L425: - `[llm].attention.clamp_kqv: float32`: Value (`C`) to clamp the values of the `Q`, `K`, and `V` tensors between (`[-C, C]`).
L426: - `[llm].attention.layer_norm_epsilon: float32`: Layer normalization epsilon.
L427: - `[llm].attention.layer_norm_rms_epsilon: float32`: Layer RMS normalization epsilon.
L428: - `[llm].attention.key_length: uint32`: The optional size of a key head, $d_k$. If not specified, it will be `n_embd / n_head`.
L429: - `[llm].attention.value_length: uint32`: The optional size of a value head, $d_v$. If not specified, it will be `n_embd / n_head`.
L430: #### RoPE
L431: 
L432: - `[llm].rope.dimension_count: uint64`: The number of rotary dimensions for RoPE.
L433: - `[llm].rope.freq_base: float32`: The base frequency for RoPE.

L544: 
L545:   - `jploski` (author of the original GGML implementation of Falcon):
L546:     ```python
L547:     # The original query_key_value tensor contains n_head_kv "kv groups",
L548:     # each consisting of n_head/n_head_kv query weights followed by one key
L549:     # and one value weight (shared by all query heads in the kv group).
L550:     # This layout makes it a big pain to work with in GGML.
L551:     # So we rearrange them here,, so that we have n_head query weights
L552:     # followed by n_head_kv key weights followed by n_head_kv value weights,
L553:     # in contiguous fashion.
L554:     if "query_key_value" in src:
L555:         qkv = model[src].view(
L556:             n_head_kv, n_head // n_head_kv + 2, head_dim, head_dim * n_head)
L557: 
L558:         q = qkv[:, :-2 ].reshape(n_head * head_dim, head_dim * n_head)
L559:         k = qkv[:, [-2]].reshape(n_head_kv * head_dim, head_dim * n_head)
L560:         v = qkv[:, [-1]].reshape(n_head_kv * head_dim, head_dim * n_head)
L561: 
L562:         model[src] = torch.cat((q,k,v)).reshape_as(model[src])
L563:     ```
