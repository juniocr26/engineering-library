**Under what precise, reproducible, source-grounded conditions can Engineering Library declare a technical document complete, correct, and ready for approval?**

## 3. Define what DONE means for documentation

Create a versioned, measurable, research-level Documentation Definition of Done.

The owner expects Engineering Library to understand the relevant source code, architecture, relationships, dependencies, behavior, tests, documentation conventions, and consequences of changes.

A complete document must cover its declared scope, not necessarily describe every source line.

Before generating a candidate, freeze:

- Project identity.
- Source revision.
- Documentation type.
- Intended audience.
- Documented interfaces and responsibilities.
- Required architecture and dependency coverage.
- Required behavior and error paths.
- Relevant tests and examples.
- Required EN/PT-BR content.
- Required documentation lifecycle action.
- Known uncertainty and out-of-scope boundaries.
- Independent verification criteria.

Never redefine completeness after seeing a generated response merely to make it pass.

### Proposed mandatory acceptance gates

G1 — SOURCE IDENTITY

Every source-dependent claim must identify the correct repository, revision, file, and relevant source evidence.

G2 — FACTUAL CORRECTNESS

No critical factual contradiction, unsupported critical behavior, invented API, or invented runtime guarantee.

G3 — ARCHITECTURAL CONTEXT

Relevant callers, callees, dependencies, configuration, state, errors, and lifecycle interactions are covered.

G4 — REQUIRED COMPLETENESS

All frozen mandatory requirements for the declared document scope are satisfied.

G5 — EXAMPLES AND TESTS

Commands, examples, and test claims are verified at the strongest authorized level. Static validation must never be described as runtime execution.

G6 — BILINGUAL SEMANTICS

English and Brazilian Portuguese preserve the same technical meaning, conditions, negations, limitations, identifiers, and code.

G7 — DOCUMENTATION MAINTENANCE

The correct ADD, MODIFY, REMOVE, NO-OP, or INCONCLUSIVE decision is supported by independently acquired repository evidence.

G8 — INDEPENDENT VERIFICATION

A separate verification procedure challenges the generated document with source evidence and negative controls.

G9 — RECOVERABILITY AND PROVENANCE

The exact candidate, sources, criteria, evaluation, model identity, and result can be reconstructed or their limitations explicitly reported.

A document must pass every applicable mandatory gate for technical acceptance.

If a gate is genuinely not applicable, record N/A with a justification established before evaluation.

Unknown or unverified critical evidence must not silently count as PASS.

## 4. Define three separate approval levels

### TECHNICALLY_ACCEPTED

The document passes all applicable frozen technical gates within its explicitly bounded scope.

### PUBLICATION_APPROVED

Technical acceptance plus authorized editorial, licensing, confidentiality, and publication review.

### TRAINING_GOLD_APPROVED

A specifically reviewed, rights-cleared example with explicit owner approval for neural training and a verified lineage and evaluation-exclusion record.

Never automatically promote a technically accepted document to publication or Gold.

The owner may approve documents without approving training use.

A neural output can be TECHNICALLY_ACCEPTED without proving general model readiness.

## 6. Establish model readiness criteria

Define a separate MODEL_READY_FOR_ASSISTED_DOCUMENTATION status.

It must not be inferred from one successful document.

Propose an initial, explicitly provisional evaluation contract using a diverse frozen set of independent documentation tasks.

As a starting research target, evaluate whether the model can achieve:

- At least 80% complete technical acceptance across a sufficiently diverse, independently reviewed task set.
- Zero critical unsupported factual claims in accepted outputs.
- Zero unsafe automatic REMOVE actions.
- At least 95% correct technical identifier preservation.
- Full mandatory EN/PT-BR coverage for accepted bilingual outputs.
- No unsupported promotion of uncertain claims.
- No regression against the unchanged baseline on matched tasks.

These are proposed engineering thresholds, not previously achieved performance or a statistical certification.

Determine whether the available independent sample is sufficient to justify any readiness conclusion.

If not, report INSUFFICIENT_EVIDENCE rather than READY.

Retain a stricter owner-controlled publication and training approval process.

- Identifier translation.
- Missing language.
- Incomplete code.
- Output truncation.
- Repetition.
- Invalid structure.
- Unsupported citations.
- Incorrect confidence.

4. Model inference.
5. Output formatting.
6. Bilingual rendering.
7. Verification.

Do not blame neural weights for failures caused by retrieval or verification.
