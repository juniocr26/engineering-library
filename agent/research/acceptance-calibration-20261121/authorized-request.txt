## 2. Define the acceptance problem precisely

The primary goal is to distinguish:

1. Source retrieval success.
2. Factual correctness.
3. Semantic source support.
4. Relevant context coverage.
5. Documentation lifecycle decision correctness.
6. Bilingual equivalence.
7. Complete-document acceptance.
8. Independent owner approval.
9. Training Gold eligibility.

A valid citation, JSON schema, exact identifier, or syntactically valid example must not independently certify a document as factually correct.

Preserve the distinction between source-reviewed manually composed documentation and complete outputs generated with neural contribution.

Do not mix heterogeneous historical attempts into a single general model accuracy statistic.

## 3. Build a measurable acceptance framework

Develop a versioned research-only acceptance protocol.

Evaluate documentation at three levels.

### Level A — Atomic factual claims

For each independently identifiable claim, record:

- Claim ID.
- Original source revision.
- Exact source evidence.
- Expected factual interpretation.
- Generated interpretation.
- Supported / contradicted / insufficient.
- Critical versus noncritical error.
- EN/PT-BR consistency.
- Reviewer and evidence provenance.

Measure supported-claim precision, unsupported-claim rate, false support, false rejection, and justified abstention.

Do not treat composite editorial groups as independent atomic claims.

### Level B — Complete documents

Evaluate:

- Factual correctness.
- Relevant completeness.
- Architecture and dependency understanding.
- API contracts.
- Error and exception behavior.
- Existing tests and their actual execution status.
- Examples and commands.
- EN/PT-BR equivalence.
- FAQ correctness.
- Citation relevance.
- Explicit limitations.

A document containing a critical unsupported factual assertion must not pass complete-document acceptance.

Report both individual dimension scores and the final complete-document outcome.

### Level C — Documentation lifecycle

Evaluate:

- ADD.
- MODIFY.
- REMOVE.
- NO-OP.
- INCONCLUSIVE.

Measure false removals, missed modifications, unsupported changes, and justified abstention separately.

A declaration missing from one file does not prove it was removed from the project.

Require independently acquired source-scope evidence before accepting REMOVE.
