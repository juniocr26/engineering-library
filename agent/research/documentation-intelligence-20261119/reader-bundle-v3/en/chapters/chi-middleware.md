# chi middleware: factory returns, deferred work and panic propagation

Status: experimental source-reviewed correction authored by Codex; human approval pending. The baseline was generated by the actual local agent. This corrected text was not supplied to that baseline and is not neural training or a published manual.

The frozen chi revision is `c64ed7d6635f33a8b2feaff7dcfa55677023ac7d`. The selected contracts are `middleware/timeout.go` and `middleware/recoverer.go`. Exact method excerpts, source hashes and physical line positions accompany this chapter in `source-excerpts.json`.

## Construction and invocation are different phases

The declaration of `Timeout` returns a function with syntax `func(next http.Handler) http.Handler`. Calling the outer function supplies a duration and obtains that middleware function. Calling the returned function supplies the next handler and constructs `http.HandlerFunc(fn)`. The request-specific work is inside the callback; returning a function literal does not execute its body.

By contrast, `Recoverer` takes the next handler in its own parameter list and returns `http.HandlerFunc(fn)` directly. An explanation that says both outer functions simply return a new handler erases the extra factory layer in the first contract. The local neural Timeout baseline made that distinction unclear. The existing deterministic return-syntax profile preserves the returned function signature and explicitly leaves the callback body unanalyzed; it does not pretend to explain the whole middleware behavior.

## Timeout: a derived context and a deferred status check

Inside the request callback, `context.WithTimeout(r.Context(), timeout)` produces the context and cancellation function. The callback registers a deferred function. That function first calls `cancel()`, then checks `ctx.Err() == context.DeadlineExceeded`. Only that equality branch calls `w.WriteHeader(http.StatusGatewayTimeout)`.

After registering the defer, the callback assigns `r = r.WithContext(ctx)` and invokes `next.ServeHTTP(w, r)`. The call is written as a normal synchronous call. This selected body contains no independent goroutine, timer-response goroutine or select that forcibly interrupts the next handler. Context propagation gives the next handler access to the derived context; it is not proof that the handler will observe or honor it.

The status operation is in the deferred body. Describing the implementation as an unconditional response that immediately arrives when a deadline passes would add behavior not present in this source. The code shown writes a status header under a specific condition; it does not construct a timeout response body or prove what a client ultimately receives after other response writes. The behavior of the context and response-writer implementations remains outside these selected methods.

The ordering of cancellation and the context-error check is part of the contract. A correction must preserve that ordering, rather than replacing it with a generic statement that a timeout returns an error. The selected callback also does not return a Go error value to a caller. Its response operation and the context error being inspected have different roles.

## Recoverer: deferred inspection after the next call begins

The request callback registers a deferred function and then invokes `next.ServeHTTP(w, r)`. Within the deferred function, `recover()` supplies the value checked by `rvr != nil`. When that condition is false, the selected recovery branch does not execute. When it is true, the first special case is `rvr == http.ErrAbortHandler`; that branch executes `panic(rvr)` before the later logging selection or status write.

For another non-nil recovered value, the code assigns `logEntry := GetLogEntry(r)`. A non-nil entry leads to `logEntry.Panic(rvr, debug.Stack())`; otherwise it calls `PrintPrettyStack(rvr)`. The getter and the logging method are different calls with different roles. These excerpts do not show an additional use of the entry to record unrelated pipeline events, nor do they declare a local variable named panic.

The final response condition is `r.Header.Get("Connection") != "Upgrade"`. Only that branch invokes `w.WriteHeader(http.StatusInternalServerError)`. The written comparison concerns the returned header value and the exact string shown. It is not evidence for a generalized classifier that recognizes every possible upgraded connection representation. The code also does not promise a replacement response body or universal success of the response write.

The neural baseline contained a critical reversed-order claim: it said deferred panic handling happens before the next function is called. A defer statement registers delayed work; it does not immediately execute that deferred function's body. Here, the direct call to the next handler follows the registration. Recovery behavior is tied to this callback's execution and panic unwinding; the selected code does not establish protection for arbitrary work in another goroutine.

## Why a keyword guard was rejected

A proposed text guard recognized the observed phrase about handling a panic before the next handler. It also matched a valid synthetic source in which an immediately invoked inner function owns the defer and completes recovery before the outer function calls the next handler. Both source snippets contain defer and a next-handler call, but their enclosing function scopes differ.

The candidate was therefore rejected without changing production validation. A future bounded AST proof would have to identify the exact enclosing callback, the deferred call and its arguments, and the direct call whose order is being described. Matching a few words in prose and source is insufficient. This rejected experiment is retained in `../../../continuation-20261119/defer-guard-candidate.json`.

## Engineer FAQ

<!-- reading-section: faq:timeout-construction -->
### Does constructing Timeout start a request or a goroutine?

No request callback is invoked by the selected outer return. `Timeout` returns a middleware factory; applying it to a handler returns the wrapped handler. The selected callback has no goroutine that forcibly stops the next handler. Deadline cooperation still depends on that handler.

<!-- reading-section: faq:panic-response -->
### Will every panic produce an HTTP 500 response?

The branch for `http.ErrAbortHandler` re-panics before logging or the later status operation. For another recovered value, the selected status call is conditional on `r.Header.Get("Connection") != "Upgrade"`. Earlier response writes and logging-helper failures are outside a guaranteed client-result claim.

<!-- reading-section: faq:helper-boundary -->
### Why keep the helper boundary explicit?

`GetLogEntry`, `logEntry.Panic` and `PrintPrettyStack` are distinct calls. This chapter reviews their selection at the call site; it does not claim a verified logging backend, durability guarantee or request-wide observability design.
